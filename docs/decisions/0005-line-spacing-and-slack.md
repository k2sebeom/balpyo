# 0005 — 줄간격은 절대값(spcPts)으로, 텍스트 박스 폭에는 안전 여유 4%를 더한다

- 상태: 확정
- 날짜: 2026-08-18
- Iteration: 1 (항목 07의 측정 — NOTES.md 01/07의 표가 근거 데이터다)
- 관련: PRD §9.3, §13-1, [지오메트리 패스](../internals/geometry-pass.md)

## 맥락

텍스트 재배치 대책의 정책은 확정되어 있었다 (PRD §13-1: 박스 크기 고정 + autofit off +
오버플로 허용, 측정 크기에 안전 여유를 더해 고정). Iteration 1의 첫 구현은 줄간격을
`a:spcPct`(배수)로 냈고 안전 여유는 미구현이었다. `01_text` 픽스처(한글·영문 혼합 3장)의
픽셀 비교와 잉크 띠 측정이 두 가지 갈라짐을 드러냈다:

1. **모든 글줄이 LibreOffice에서 8~13px 아래로 밀렸다.** `spcPct`의 기준이 엔진마다
   다르다 — CSS `line-height` 배수는 **폰트 크기** 기준이지만, LibreOffice는 **폰트 고유
   줄 높이**(ascent+descent, Noto Sans는 ≈1.36em) 기준으로 해석한다. 같은 150%가 웹에서
   1.5em, LibreOffice에서 ≈2.04em이 된다.
2. **여유 폭 2.4%였던 본문이 LibreOffice에서 1줄 → 2줄로 갈라졌다.** LibreOffice는
   한글↔라틴 스크립트 경계마다 간격을 넣어(스크립트 간격 — DrawingML 속성으로 끌 수
   없다) 혼합 문자 줄을 최대 **+3.3%** 넓게 그린다. 박스를 측정 폭 그대로 고정하면 줄 끝
   여유가 그보다 작은 줄은 마지막 낱말이 다음 줄로 넘어간다.

## 선택지

줄간격:

1. **`spcPct` 유지 + 픽셀 허용 오차 확대.** 오프셋 8~13px은 "한 줄 차이" 수준을 넘는
   상시 편차이고, 허용 오차를 그만큼 열면 픽셀 비교가 아무것도 감시하지 못한다.
2. **`spcPts`(절대 1/100 pt) 전환.** 확정된 배수 × 폰트 크기를 렌더러 경계에서 절대값으로
   눕힌다. 두 엔진이 같은 줄 전진 폭을 쓰게 되고, 남는 것은 첫 기준선 배치의 엔진 차
   (+2~5px 측정)뿐이다. CSS 쪽은 그대로 배수를 쓴다 — 같은 확정 값(배수)의 타깃별 표현일
   뿐이다.

안전 여유:

1. **없음 (측정 폭 그대로).** 측정으로 반증되었다 — 여유 2.4% < 스크립트 간격 3.3%.
2. **폭 +4%, 정렬 방향 고려.** 측정 최대치(+3.3%)에 여유를 더한 값. 글자가 닻을 내린
   변은 고정한다: start는 오른쪽으로만, center는 양쪽 반씩, end는 왼쪽으로만 넓혀 글자
   위치가 웹과 같게 남는다. justify는 넓히지 않는다 — 양쪽 정렬은 글줄을 박스 폭까지
   늘이므로 넓히면 웹보다 긴 글줄이 된다.
3. **더 큰 여유 (10%+).** 반대 방향의 위험이 커진다: 웹이 다음 줄로 넘긴 낱말이 넓힌
   박스에 들어가면 줄이 **줄어드는** 갈라짐이 생긴다. 여유는 엔진 폭 오차는 덮되 낱말
   하나 폭보다는 작아야 한다.

## 결정

**줄간격은 `spcPts`, 안전 여유는 폭 +4% (정렬 방향 고려, justify 제외).**
구현은 `render/pptx/units.go`(LineSpacing)와 `render/pptx/shape.go`(TextBoxRect)다.

## 근거

측정값 (컨테이너의 고정 환경, `01_text`, 요소 7개 — 전체 표는 NOTES.md 01/07):

- 줄 수: spcPts + 여유 4% 적용 후 **7/7 요소에서 웹과 LibreOffice가 일치** (적용 전
  본문 1줄 vs 2줄).
- 글줄 잉크 세로 중심: +2~5px (spcPct 시절 +8~13px).
- 글줄 잉크 폭: −1.5% ~ +3.3%.
- 픽셀 diff(채널 32 초과 비율): 슬라이드별 1.2~2.1%.

이 수치가 곧 회귀 감시선이 되었다 (PRD §13-1에 기입): 줄 수 차이 0, 세로 중심 ±6px,
잉크 폭 ±4%, 픽셀 비율 2.5%. `internal/testkit`의 잉크 띠 테스트
(`TestFixtureLineBreaksMatchLibreOffice`)와 픽셀 비교가 감시한다.

## 결과

- 항목 05가 남긴 "spcPct와 CSS line-height는 기준이 다를 수 있다"는 열린 질문이 측정으로
  닫혔다 — spcPct를 쓰는 코드는 남아 있지 않다.
- 스크립트 간격은 LibreOffice 렌더러의 동작이므로 PowerPoint/Keynote에서는 웹에 더
  가깝게 나올 수 있다 — 사람이 여는 리뷰(TASKS ③)에서 확인한다.
- justify 정렬은 여유가 없어 스크립트 간격 위험이 남는다 — justify를 쓰는 픽스처가
  생기는 시점에 다시 측정한다.
