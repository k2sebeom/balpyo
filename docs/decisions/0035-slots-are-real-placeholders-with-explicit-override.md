# 0035 — 슬롯은 진짜 PPTX 플레이스홀더가 되고, 명시 xfrm/rPr로 패리티를 지킨다

- 상태: 확정
- 날짜: 2026-09-14
- 마일스톤: M1.2 (슬롯 → PPTX 플레이스홀더 — TASKS.md)
- 관련: PRD §7.3(1층 레이아웃과 슬롯), §9.3(computed-style 역추론 없음), §9.5(§826 슬롯 →
  플레이스홀더), [layouts.md](../reference/layouts.md), ADR 0032(슬라이드 어휘는 core가
  검사한다)

## 맥락

1층 레이아웃 슬라이드는 **테마가 배치를 소유**하고 저자는 슬롯에 콘텐츠만 넣는다 (PRD §7.3).
`slot="title"` 속성은 이미 파서가 받지만(SlotAttr — 슬라이드 직계 자식이 될 수 있는 요소
전부에 열려 있다) **아무도 소비하지 않는다**: core가 검증하지 않고, 덱 모델이 나르지 않고,
두 렌더러가 무시한다. 이 결정은 슬롯을 실체로 만드는 것이다 — 웹의 배치 영역과 **PPTX의
진짜 플레이스홀더**(PRD §826) 둘 다로.

핵심 긴장: balpyo의 계약(§9.3)은 **모든 좌표·외관이 명시적이고 브라우저가 잰 값**이라
웹과 PPTX가 픽셀 단위로 같다는 것이다. 그런데 OOXML 플레이스홀더는 위치·텍스트 스타일을
**마스터에서 상속**한다 — 그대로 두면 이 아키텍처가 존재하는 이유인 웹/PPTX 갈라짐이 다시
들어온다.

## 선택지

1. **레이아웃 영역만, 도형은 절대 박스 그대로** — 슬롯을 grid-area로만 실현하고 PPTX는
   지금처럼 명시 좌표 텍스트 박스로 둔다. 패리티는 완벽하지만 PowerPoint가 도형을 제목/본문
   **플레이스홀더로 인식하지 못한다** (개요 보기·레이아웃 재설정·"제목을 클릭해 입력" 없음).
2. **진짜 플레이스홀더 + 마스터 상속** — PRD §826을 글자 그대로. `p:ph`를 슬라이드 레이아웃에
   등록하고 위치·스타일을 마스터에서 상속. PowerPoint 네이티브지만 명시-전부 패리티 계약이
   깨진다.
3. **진짜 플레이스홀더 정체 + 명시 xfrm/rPr 오버라이드** — 슬라이드 도형이 `<p:ph type=..
   idx=..>`로 레이아웃의 플레이스홀더를 **가리키되**, 잰 xfrm과 해석된 rPr을 그대로 실어
   기본값을 덮는다.

## 결정

**선택지 3.** 슬롯을 가진 단일 프레임 도형(`<text>`·서브셋 블록·`<ul>/<ol>`·`<shape>`·
`<image>`)은 `<p:nvPr>` 안에 `<p:ph type=".." idx=".."/>`를 얻고, **동시에** 잰 좌표(xfrm)와
해석된 외관(rPr/pPr)을 지금과 똑같이 명시한다. 사용된 각 레이아웃은 자기 슬롯들의 플레이스홀더를
기본 좌표와 함께 선언하는 `p:sldLayout` 파트를 얻고, 마스터는 제목/본문 텍스트 스타일
(`p:txStyles`)을 얻는다.

- **슬롯 어휘는 닫혀 있고 core가 검사한다** (ADR 0032의 `layout`과 같은 태도): 레이아웃별
  슬롯 목록은 PRD §7.3의 고정 카탈로그이므로 `soml`이 소유하고, 없는 슬롯 이름은 **line:col을
  가진 빌드 에러**다. 슬롯→`p:ph` 타입/idx 매핑도 표준이라 `soml`이 소유한다.
- **슬롯의 시각 위치(grid-area)는 테마가 소유한다**: `layouts/*.css`가 `grid-template-areas`로
  영역을 정하고 렌더러가 슬롯 자식마다 `grid-area: <슬롯>`을 얹는다. 어휘(무엇이 유효한가)는
  core, 배치(어디에 놓이는가)는 테마 — M1.1의 스테이지 배치 CSS 경계와 같은 선이다.
- **플레이스홀더는 단일 프레임 슬롯에만 붙는다.** 컨테이너를 담은 슬롯(`<col slot="left">`)은
  플레이스홀더가 되지 않는다 — 플레이스홀더는 프레임 하나이고, 레이아웃 컨테이너는 좌표로
  구워져 사라지며 자식만 절대 도형으로 남기 때문이다 (writeShapeNode). 컨테이너 슬롯은 웹
  영역만 얻고 PPTX에서는 자식 도형들이 지금처럼 절대 좌표로 나온다.

## 근거

- **정체는 레이아웃에서, 위치·외관은 슬라이드에서 — 둘은 충돌하지 않는다.** OOXML 플레이스홀더는
  슬라이드 도형에 명시 `xfrm`이 있으면 그것이 마스터 기본값을 **이긴다** (rPr도 같다). 그래서
  선택지 3은 "as-authored" 렌더가 웹과 픽셀 단위로 같은 채로(명시 값이 이긴다) PowerPoint
  네이티브 편집(제목/본문 인식, 개요 보기, 레이아웃 재설정)을 얻는다. 유일한 패리티 "깨짐"은
  사용자가 PowerPoint에서 **레이아웃 재설정**을 직접 누를 때인데, 그것은 우리 산출물의 갈라짐이
  아니라 사용자 행동이다 — 선택지 2가 **모든** 슬라이드를 열자마자 갈라뜨리는 것과 다르다.
- **선택지 1을 버린 이유**는 슬롯의 제품 약속이 "테마가 배치를 소유하고 저자는 의도만
  선언"(PRD §7.3)이라는 것이고, 그 약속의 PPTX 쪽 절반이 **진짜 플레이스홀더**라는 것이다
  (PRD §826은 이를 명시한다). 영역만으로는 웹에서만 슬롯이 슬롯이고 PPTX에서는 그냥 텍스트
  박스다.
- **슬롯 어휘를 core에 둔 이유**는 `layout`과 같다 (ADR 0032): 오타(`slot="titel"`)가 조용히
  기본 슬롯으로 떨어지면 콘텐츠가 엉뚱한 자리에 놓이고 그 실패는 렌더를 볼 때까지 안 보인다.
  닫힌 어휘가 그것을 빌드 실패로 만든다.
- **단일 프레임에만 플레이스홀더를 붙인 이유**는 매핑을 정직하게 유지하기 위해서다. 플레이스홀더는
  프레임 하나(하나의 txBody 또는 그림)인데 `<col slot="left">`는 여러 도형으로 펼쳐진다 —
  컨테이너를 한 플레이스홀더로 접으면 그 안의 카드·텍스트를 담을 곳이 없다. 컨테이너 슬롯은
  웹에서 grid-area를 얻어 배치되고, 그 안의 절대 좌표 도형들은 지금의 매핑 그대로다.

## 결과

- `soml`: 레이아웃별 슬롯 카탈로그(PRD §7.3)와 슬롯→(phType, idx) 표준 매핑. 요소가 확정 슬롯을
  나른다 (Placement 곁 또는 Appearance.Slot).
- `core/resolve.go`: 슬라이드 직계 자식의 `slot=`을 레이아웃 슬롯 어휘로 검증(없는 슬롯 →
  진단), 확정 슬롯을 요소에 싣는다. 슬롯은 슬라이드 직계 자식에만 유효(중첩 `slot=` → 진단).
- `render/web`: 슬롯 자식에 `grid-area: <슬롯>`(또는 `balpyo-slot-<이름>` 클래스). 테마
  `layouts/*.css`가 `grid-template-areas`로 영역을 정의.
- `render/pptx`: 슬롯 단일 프레임 도형의 `<p:nvPr>`에 `<p:ph>`; 사용된 레이아웃마다 슬롯
  플레이스홀더 + 기본 좌표를 선언하는 `p:sldLayout` 파트; 마스터 `p:txStyles`; 슬라이드가
  자기 레이아웃 파트를 가리키도록 관계 재배선.
- 픽스처: 레이아웃별 슬롯 정상 케이스 + 없는 슬롯 빌드 에러 + `p:ph`/`p:sldLayout` 구조
  어서션 + 웹 grid-area 골든 + 픽셀 비교.
- `docs/reference/layouts.md`에 슬롯 표(레이아웃별 슬롯·phType·영역).
