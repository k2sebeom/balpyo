# 테스트 환경

balpyo의 테스트는 두 렌더러가 **같은 그림을 낸다**는 것을 검사한다. 그 비교는 렌더 환경이
결정적일 때만 의미가 있으므로, 테스트는 항상 고정된 Docker 이미지 안에서 돈다.

```
make test      # 컨테이너 안에서 전체 테스트
make review    # 웹/PPTX/diff 이미지를 review/ 에 남기고 갤러리를 만든다
make golden    # 골든 갱신
make versions  # 이미지에 실제로 설치된 버전 출력
make shell     # 컨테이너 안에서 셸 (디버깅)
```

## 테스트 이미지

`docker/test.Dockerfile` 하나가 환경 전체를 소유한다.

| 도구 | 역할 |
|---|---|
| **LibreOffice**(impress, headless) | PPTX 열림 테스트, PPTX → PDF 렌더 |
| **Chromium** | 지오메트리 패스, 웹 스크린샷 |
| **poppler-utils**(`pdftoppm`) | PDF → PNG |
| **Noto Sans / Noto Sans CJK KR** | 텍스트 메트릭의 유일한 폰트 집합 |

결정성을 만드는 장치:

- **베이스 이미지를 패치 버전까지 고정한다** (`golang:1.26.6-bookworm`). Debian bookworm의
  apt 저장소는 릴리스 안에서 패키지 버전을 고정하므로 LibreOffice와 Chromium이 함께 고정된다.
- **폰트는 Noto만 설치한다.** 폰트 집합이 환경마다 다르면 줄바꿈 위치가 달라지고, 픽셀
  비교는 물론 지오메트리 패스가 잰 박스 크기까지 흔들린다.
- **힌팅과 LCD 서브픽셀을 끈다** (`docker/fonts.conf` + Chromium 플래그). 힌팅은 글리프를
  픽셀 그리드에 맞추느라 글자 폭을 바꾼다 — 끄면 브라우저와 LibreOffice의 텍스트 폭이
  서로, 그리고 실행마다 더 잘 맞는다.
- **버전을 이미지 안에 기록한다** (`/etc/balpyo-versions.txt`). `docker/versions.env`의
  기대값과 대조하는 테스트가 있어, 보안 패치로 버전이 움직이면 골든이 조용히 깨지는 대신
  그 테스트가 먼저 실패한다. 비교는 **접두 일치**다 — `LibreOffice 7.4.7.2`가
  `LibreOffice 7.4.7.2 40(Build:2)`를 통과시킨다 (뒤쪽 빌드 문자열은 렌더와 무관하다).

버전이 움직였을 때의 절차: `make versions`로 실제 값을 보고 → `docker/versions.env`를
갱신하고 → `make golden`으로 골든을 다시 뜬 뒤 → **골든 diff를 눈으로 확인**하고 두 변경을
같은 커밋에 담는다.

### 컨테이너 실행 방식

- 컨테이너 런타임은 자동으로 고른다: `docker`가 실제로 동작하면 docker, 아니면 `finch`.
  `command -v`로 판단하지 않는 이유는 동작하지 않는 docker 심(shim)이 PATH에 있는 환경이
  흔하기 때문이다. `make test DOCKER=podman`으로 덮어쓸 수 있다.
- **컨테이너는 네트워크 없이 돈다** (`GOPROXY=off`). 의존성은 호스트 모듈 캐시를 마운트해
  공급하므로 `make test`가 먼저 호스트에서 `go mod download`(= `make deps`)를 돌린다.
- Go 빌드 캐시는 명명 볼륨(`balpyo-gocache`)에 남는다 — 매 실행마다 전체 컴파일을 반복하지
  않는다.
- 이미지는 `docker/` 아래 파일이 바뀔 때만 다시 빌드한다 (`.make/image.stamp`).

### 호스트에서 돌리기

`make test-host`는 컨테이너 없이 `go test ./...`를 돌린다. 빠른 되풀이용이며, LibreOffice·
Chromium이 없으면 그 테스트들은 **건너뛴다**.

건너뛰기의 범위는 도구마다 다르다. **Chromium이 없으면 픽스처 스위트 전체가 건너뛰어진다** —
골든 비교만 돌릴 수도 없다. 빌드가 지오메트리 패스로 박스를 재고 그 수치가 곧 산출물이기
때문이다 (`Fixture.Build`가 정책을 적용하는 자리다). 브라우저는 있고 LibreOffice만 없으면
골든 비교는 돌고 렌더 비교(`render` 서브테스트)만 건너뛴다. 즉 도구가 하나도 없는 호스트에서
`make test-host`가 실제로 판정하는 것은 파서·모델·렌더러의 단위 테스트다.

건너뛰기가 거짓 초록이 되지 않게 하는 장치가 `BALPYO_TEST_STRICT=1`이다. 이미지가 이 값을
켜므로 컨테이너 안에서는 도구가 없을 때 건너뛰지 않고 **실패**한다. 즉 로컬 초록은 "골든은
맞다"까지만 뜻하고, 렌더 비교의 초록은 `make test`만이 준다.

하네스가 읽는 환경 변수:

| 변수 | 뜻 |
|---|---|
| `BALPYO_TEST_STRICT` | 1이면 외부 도구 없음을 실패로 본다 (이미지가 켠다) |
| `BALPYO_UPDATE_GOLDEN` | 1이면 골든을 비교하지 않고 쓴다 (`make golden`) |
| `BALPYO_REVIEW` | 1이면 리뷰 갤러리를 남긴다 (`make review`) |
| `BALPYO_CHROMIUM` / `BALPYO_SOFFICE` / `BALPYO_PDFTOPPM` | 실행 파일 경로 |
| `BALPYO_CHROMIUM_NO_SANDBOX` | 1이면 `--no-sandbox` (컨테이너는 root라 필수) |

## 픽스처

픽스처 하나(`testdata/fixtures/<NN>_<이름>/`)는 **완전한 balpyo 프로젝트**다. 그래서 사람이
그 디렉토리를 직접 빌드해 결과를 볼 수 있다.

```bash
go run ./cmd/balpyo build --project testdata/fixtures/00_empty --target html,pptx
```

```
00_empty/
├── balpyo.json          # 덱 설정 (없으면 기본값)
├── slides/*.slide       # 입력
├── assets/*.png         # 그림 입력 (그림이 있는 픽스처만 — 05_image)
└── golden/              # 산출물 스냅샷 (사람이 커밋한다)
    ├── index.html       #   웹 타깃
    ├── assets/**        #   웹이 낸 에셋 바이트 (입력과 같아야 한다)
    ├── diagnostics.txt  #   경고가 있을 때만
    └── pptx/**          #   PPTX 파트별 XML (zip을 푼 것) + ppt/media/** 바이트
```

- 접두 숫자는 iteration 순서이자 스위트 실행 순서다.
- `_`로 시작하는 디렉토리는 수집되지 않는다 (작업 중 픽스처). 슬라이드 수집 규칙과 같은 관례다.
- 빌드 산출물은 임시 디렉토리에 쓴다 — 픽스처 디렉토리에는 **입력과 골든만** 남는다.

## 골든

골든은 `make golden`으로만 갱신하고, 손으로 쓰지 않는다. 골든 변경은 구현 변경과 **같은
커밋**에 담아 "무엇이 왜 움직였는지"를 기록에 남긴다. 갱신 실행은 내용이 같은 파일을
건드리지 않으므로, 나온 diff는 실제로 움직인 골든만 담는다.

**PPTX는 zip 바이트가 아니라 파트별 XML을 골든으로 남긴다.** 이유가 두 개다.

1. zip 바이트는 압축기 구현이 바뀌면 내용이 같은데도 달라진다 (zip 엔트리 시각은 이미
   1980-01-01로 고정해 두었다).
2. 무엇보다 **XML 골든은 git diff에서 읽힌다.** "도형이 하나 늘었다", "리터럴 RGB가
   `schemeClr` 참조를 밀어냈다"가 diff로 보이는 것이 이 골든의 목적이다.

골든 트리 비교는 **남은 골든도 잡는다.** 산출 파일 이름이 바뀌거나 사라지면 옛 골든이
아무도 보지 않는 채로 남아 통과하기 때문이다. 갱신 모드는 그런 파일을 지운다.

### 바이너리 골든 — 그림이 들어온 뒤

Iteration 5까지 골든은 전부 텍스트였다. 그림 픽스처(`05_image`)가 그것을 깬다: 웹 산출물의
`assets/*`와 PPTX의 `ppt/media/*`가 골든에 **바이트로** 들어간다 (같은 그림이 두 번 — 타깃마다
한 번).

- 그래서 **에셋은 작게 만든다.** 픽스처의 네 장은 합계 6.3KB이고 PNG는 8비트 팔레트로 저장했다
  (1200×600이 460B — RGB로 저장하면 3,022B다). 저장소가 이 크기의 대가를 영구히, 두 배로 낸다.
- 바이너리 골든은 diff에서 읽히지 않으므로 **읽히는 판정을 따로 둔다**: 웹 산출 에셋과 PPTX
  미디어 파트가 **커밋된 입력 파일과 바이트가 같은지**, 파트 이름이 에셋 표 순서와 포맷
  확장자를 따르는지, 남는 파트가 없는지를 단정한다
  (`TestImageFixtureAssetsAreByteIdentical`). 엔진이 그림을 고치지 않는다는 계약(리사이즈·
  재압축·EXIF 회전 없음)이 이 테스트로만 자동 판정된다.
- 픽스처의 에셋 넷이 PNG 색 타입 두 가지(팔레트·RGB)와 포맷 두 가지(PNG·JPEG)를 함께 담는다 —
  덱에 든 포맷만 `[Content_Types].xml`의 `Default`가 되므로 그 분기도 골든에 보인다.

### 토큰이 눕지 않는다 — 색 계약의 자동 판정

골든 위에 서 있는 계약 하나가 이 제품의 핵심이다: **토큰으로 선언한 색은 슬라이드 파트에서
`schemeClr` 참조로 남고 리터럴만 `srgbClr`로 나온다** ([외관 속성](../reference/appearance.md)).

Iteration 3까지 이 검사는 "슬라이드 파트에 `srgbClr` 0건"이었다 — 리터럴 색이 어휘에 없던
그 세 iteration에서는 그 문장이 "토큰이 눕지 않는다"와 **같은 문장**이었다. Iteration 4가
`fill="#0F65F9"`를 열면서 두 문장이 갈라진다: 리터럴이 `srgbClr`로 나오는 것은 정상이고,
토큰이 `srgbClr`로 나오는 것은 계약 위반이다.

그래서 검사는 **슬라이드별 리터럴 색 전수 표**와 산출 XML을 정확히 맞댄다 (표의 열쇠는 파트
번호가 아니라 `cSld@name`의 슬라이드 id다). 슬라이드를 예외로 빼는 길을 버린 이유: 그러면
리터럴이 있는 슬라이드에서 계약이 아예 없어지고, **같은 슬라이드의 토큰 색**이 눕는 것을
아무것도 보지 않는다. 값을 표에 적으면 예상 밖의 리터럴과 토큰의 눕음이 함께 걸린다 —
계약이 오히려 강해진다.

`04_shape` 픽스처의 `003_literal_colors`가 그 표의 유일한 항목이고, 그 슬라이드가 쓰는
`#0F65F9`는 **`accent1`과 같은 RGB**다 — 같은 색이 어떻게 선언되었는지에 따라 산출물이
갈라지는 것을 눈으로는 구별할 수 없다는 사실을 픽스처가 못 박는다.

## 렌더 비교

`make test`의 마지막 단계는 픽스처마다 도는 두 갈래 렌더 비교다.

```
.slide → 덱 모델 → HTML  → Chromium → 요소 스크린샷 ─┐
                 → PPTX  → LibreOffice → PDF → pdftoppm → PNG ─┴→ 픽셀 diff
```

- **PPTX 열림 검사는 "열린다"로 만족하지 않는다.** PowerPoint와 LibreOffice는 깨진 패키지를
  조용히 복구해서 열어 주므로, 복구가 일어나면 사용자는 파일을 열 때마다 경고를 본다.
  그래서 stderr에서 무해한 줄(javaldx, fontconfig, dbus)을 걷어낸 뒤 **남은 것이 있으면
  실패**로 본다.
- **PNG 크기는 pdftoppm에 목표 크기로 직접 준다** (`-scale-to-x/-scale-to-y`). DPI로 맞추면
  페이지 크기 반올림 때문에 한두 px씩 어긋난다.
- **웹 스크린샷은 요소의 문서 좌표 사각형을 clip으로 잘라 찍는다** (CDP
  `Page.captureScreenshot` + `captureBeyondViewport`). 요소를 뷰포트로 스크롤한 뒤 찍는
  방식은 슬라이드가 뷰포트보다 클 때 잘라낸 영역이 스크롤량만큼 어긋나고 뷰포트 밖이 페이지
  배경으로 채워진다 — 그러면 픽셀 비교가 렌더 차이가 아니라 스크린샷 버그를 보고한다.
  좌표는 지오메트리 패스가 쓰는 것과 **같은 JS 스니펫**에서 얻는다.
- 허용 오차는 **두 값**이다: 채널당 차이(기본 32)와 그 값을 넘은 픽셀의 비율(기본 2%).
  텍스트 안티앨리어싱은 글자 경계 픽셀의 채널을 크게 흔들지만 흔드는 픽셀 수는 적다 —
  채널 허용값만 키우면 색이 조금 틀린 큰 면적을 놓치고, 비율만 키우면 글자가 굵어진 것을
  놓친다. 실제 텍스트로 측정한 값은 Iteration 1에서 이 기본값을 대체한다.
- **오차 조정의 범위는 근거의 범위와 같다.** 픽스처마다 측정값에 여유를 더한 조정이 있고
  (레이아웃 픽스처는 3.2% — 슬라이드당 텍스트 박스가 늘어 첫 기준선 잔차가 박스 수에 비례해
  쌓인다), 근거가 슬라이드 하나에만 있으면 **그 슬라이드에만** 준다: `style` 탈출구로 외관을
  쓴 슬라이드는 웹 전용 칠이 들어가 두 렌더가 다른 것이 계약 그 자체다
  ([ADR 0014](../decisions/0014-style-escape-hatch-boundary.md)). 같은 수치를 픽스처 전체에
  주면 나머지 슬라이드의 **실제** 배치 갈라짐이 그 그늘에 숨는다.
- **모양이 다르면 오차를 키우지 않는다.** 텍스트 픽스처의 잔차는 글리프 경계 픽셀이지만
  도형은 면이라 두 렌더가 다르면 **모양이 다른 것**이고, 그것은 오차 조정으로 덮을 대상이
  아니라 기하 유도(`render/web`의 프리셋 표)와 조정값 평가(`pptx.AdjustValue`)를 고칠 신호다.
  그런데 슬라이드 하나의 비율로는 프리셋 하나의 갈라짐이 12분의 1로 희석되므로, 12종이 격자에
  있다는 구조를 이용해 **도형마다 크롭을 잘라** 수치를 남긴다 (여유 16px = 테두리 번짐 +
  `callout` 꼬리 12.5%, 격자 간격 24px보다 작아 이웃 도형이 들어오지 않는다). 측정:

  | 프리셋 | 오차 | 프리셋 | 오차 |
  |---|---|---|---|
  | `ellipse` | 2.90% | `hexagon` | 3.74% |
  | `star` | 3.45% | `rect` | 4.71% |
  | `callout` | 3.63% | `cylinder` | 4.73% |
  | `chevron` | 3.66% | `diamond` | 4.90% |
  | `rounded-rect` | 4.71% | `arrow-right` | 5.74% |
  | | | `cloud` | 6.04% |
  | | | `parallelogram` | 7.95% |

  **오차의 순서가 정체를 말한다**: 큰 쪽은 긴 사선 테두리를 가진 프리셋이고 작은 쪽은 매끄러운
  곡선이다 — 남은 차이는 굵기 1px 외곽선의 반 픽셀 반올림이 두 래스터라이저에서 다르게 떨어지는
  것이다 (경로 중앙 규약이라 둘레 전체가 다른 픽셀로 세어진다). 기하가 어긋나면 오차는 이 폭이
  아니라 어긋난 **면적**으로 나타난다. 그래서 슬라이드 단위 비율은 잔차만 남은 수치가 되고
  (도형 픽스처 3.7%, 도형이 가장 많은 카드 슬라이드 5.2%), 기하·줄 수 판정은 각자의 검사가
  갖는다.
- **그림도 하나씩 잰다** (`TestImageFixturePictureRegions`) — 판정이 하나 늘었다. 근거는 도형과
  같다: 슬라이드 하나의 비율로는 크롭 축이 뒤바뀐 그림 한 장이 스물넷 중 하나로 희석된다.
  그림의 **잰 rect**를 두 렌더에서 잘라 대조하고(그림 24장), 허용은 **6% + 절대 하한 32픽셀**이다.
  도형과 다른 두 가지가 있다.
    - **여유 없이 잰 rect를 자른다.** 그림자·회전 외접 사각형·경계 중앙의 `a:ln`은 rect 밖
      24px까지 퍼지지만, 픽스처의 가장 좁은 칸 간격이 `gap="md"` = 24px이라 여유를 그만큼 주면
      **이웃 그림이 크롭에 들어와** 오차의 주인이 흐려진다 (도형은 여유 16px < 간격 24px으로 그
      문제를 피했다). 밖으로 나간 잉크는 슬라이드 전체 비교가 본다.
    - **비율에 절대 하한이 붙는다.** 잔차는 표식 경계 한 줄에 남으므로 픽셀 **수**가 그림 크기와
      무의존인데 비율은 면적으로 나눈 값이다 — 16×8(=128픽셀) 그림에서 경계 20픽셀이 13.9%다.
      방법의 전제가 깨지는 자리이므로 비율을 키우는 대신(그러면 큰 그림의 판정이 함께 무력해진다)
      하한을 두었다. 크롭 축이 갈라질 수 있는 `cover` 그림은 전부 17,000픽셀 이상이라 이 하한이
      판정에 닿지 않는다. 측정: 최대가 002의 **테두리 그림 4.87%**(200×101, 993픽셀), 최소가
      006의 전면 그림 **0.21%**(1152×360)다. 4.87%의 정체는 CSS 테두리(박스 안쪽)와 OOXML
      `a:ln`(경계 중앙)의 차이이고, 보정하지 않는 대가가 1px 테두리에서 그 값이다.
- **도형 수 등식이 두 태그를 함께 센다.** `<image>`는 `p:pic`이 되므로 `p:sp`만 세면 그림이 든
  슬라이드에서 등식이 어긋난다 (그림 픽스처 측정: `측정 박스 68 − 컨테이너 20 − spacer 1 = 도형
  47`). 좌표 대조는 그림에서도 **0 오차**다 — `pad`가 붙은 칸까지 포함해서 잰 rect의 EMU가 곧
  `xfrm`이다.
- **전제가 깨지는 검사는 값을 키우지 않고 건너뛴다.** 잉크 띠 판정은 "가장 흔한 색이 배경,
  잉크는 글자"에 기대는데, 저자가 칠한 사각형은 하나의 거대한 띠가 되어 글자를 재는 방법이
  성립하지 않는다 — 오차를 키워 통과시키는 대신 "여기서는 이 방법을 쓸 수 없다"를 표로 적는다
  (`inkBandSkipSlides`). 그 슬라이드의 좌표는 여전히 0 오차로 못 박혀 있다.
- **도형 픽스처에서는 그 전제가 슬라이드 단위로 깨진다.** 도형은 면이므로 대부분의 슬라이드가
  칠해져 있다 — 12종 슬라이드의 첫 줄 도형 넉 장이 1103×112px 띠 **하나**가 된다 (글줄 넷이
  아니다). 그래서 `04_shape`의 여덟 장을 모두 건너뛰고, **판정을 도형 안쪽으로 옮긴다**:
  도형의 잰 rect 안에서는 가장 흔한 색이 채움이고 잉크는 글자다. 영역은 잰 rect를 테두리
  굵기만큼, 그리고 둥근 모서리에서는 **반경만큼 더** 줄인 것이다 (모서리에는 도형 밖 흰색이
  남아 그 행이 하나의 띠로 세어진다 — radius=32 도형이 글줄 하나인데 띠 셋으로 읽혔다).
  채움이 잰 rect를 덮지 않는 프리셋(diamond·chevron …)에서는 이 방법도 성립하지 않아 목록으로
  닫아 두었다 (`inShapeBandPresets` = rect·rounded-rect).
- **그림 픽스처에서는 잉크 띠 판정을 일곱 슬라이드 전부에서 건너뛴다.** 도형이 깨뜨린 전제가
  그림에서는 더 크게 깨져서, 판정이 "허용 오차를 넘었다"가 아니라 **`띠에 주인이 없다`**로 죽는다
  (잰 줄이 없는 자리에 잉크가 있다 — 001의 첫 줄 그림 넷이 1068×202px 띠 하나, 006의 전면 그림이
  1152×360px 띠 하나다). 더 나쁜 경우를 실물로 봤다: 004처럼 그림 옆에 글이 있으면 그림 띠가
  글줄과 겹쳐 **주인을 찾아 통과하는데**, 그때 재는 것은 글자가 아니라 그림이다. 도형처럼 판정을
  안쪽으로 옮길 수도 없다 (그림 안에는 글자가 없다). 잃지 않는 것: 슬라이드 직속 텍스트의 줄바꿈
  계약은 01~03 픽스처가 같은 검사로 지키고, 그림의 자리는 좌표 대조가 0 오차로, 그림의 내용은
  위의 그림별 크롭 비교가 판정한다. 되살릴 방법도 정해져 있다 — **그림의 잰 rect와 겹치지 않는
  띠만** 판정하면 전제가 살아난다 (하네스 변경이라 아직 하지 않았다).
- **겹침 슬라이드에서는 겹친 영역을 잘라 대조한다** (`TestStackFixtureOverlapRegions`,
  Iteration 6). 두 자식이 겹친 사각형을 두 렌더에서 잘라 픽셀을 맞대고, 허용은
  `stackOverlapRegionDiffMaxRatio = 6%`다. 근거는 순서의 민감도다 — 겹침 순서가 뒤집히면 그
  영역 전체가 다른 색이 되어 ~100%로 튀므로 6%가 뒤집힘을 넉넉히 잡는다. 측정: `04_z_order`의
  **muted∩accent1(divergence 자리) = 2.627%**(136×156px), `accent1∩fg = 1.422%`(112×102px).
  둘 다 여유 안이고, 이 크롭이 항목 04의 "자식마다 `position:relative`로 칠 순서를 문서 순서로
  되돌린다"를 픽셀로 판정한다 (그 한 줄이 빠지면 muted∩accent1 자리가 두 타깃에서 갈라진다).
- **겹친 영역 크롭에도 절대 하한이 붙는다** (`stackOverlapMinSide = 24px`, 그림 크롭의 하한과
  같은 자리의 장치). muted∩fg의 16×66px 슬리버는 **12%**였는데 이는 z-순서 뒤집힘이 아니라
  두 래스터라이저가 세로 색 경계 한 줄(≈129px)을 다르게 리샘플링한 것이다(그림 리샘플링과 같은
  잔차) — 얇은 띠에서 큰 비율이 된다. 그 쌍의 순서(fg가 위)는 `accent1∩fg`가 이미 판정하므로
  짧은 변이 24px 미만인 겹침은 건너뛴다. 핵심 divergence(136×156px)는 남는다.
- **겹침에서 잉크 띠 판정을 건너뛴다** (그림·도형과 같은 이유가 여기서도 성립한다). 겹친
  자리에는 잰 줄 하나에 띠 하나가 대응하지 않는다 — 여러 층이 한 자리에 있으므로 "띠에 주인이
  없다". 잃지 않는 것: 겹침 **없는** 텍스트(`010_content_explicit`)와 01~03 픽스처가 줄바꿈
  계약을 같은 검사로 지키고, 겹친 자리의 색은 위의 영역 크롭이 판정한다.
- **겹침의 좌표 대조는 일치는 보지만 옳음은 보지 않는다.** `TestFixtureCoordinatesMatchGeometry`는
  웹이 잰 좌표가 PPTX의 `xfrm` EMU와 **같은지**만 본다 (0 오차). 웹에서 앵커가 엉뚱한 자리에
  붙으면 PPTX도 같이 틀리므로 이 검사는 통과한다 — 이 자동 검사가 보증하는 것은 "두 타깃이
  일치한다"까지다. **옳음의 판정자는 항목 04의 좌표 스냅샷(브라우저가 잰 절댓값을 못 박는다)과
  항목 06의 사람 확인**이다 (`stack-deck.pptx`를 열어 배지 위치·겹침 순서·독립 객체 여부를 본다).
- **겹침 픽스처의 슬라이드별 조정** (근거의 범위 = 조정의 범위): `06_stack/in-container`는 3.7%
  (그림 카드 리샘플링 + 라벨 + 외곽선 도형 + 문단이 한 슬라이드에 모인 잔차의 합, 측정 3.128%),
  `06_stack/content-explicit`는 3.0%(겹침 **없는** 순수 텍스트, h1 큰 글리프 + 첫 기준선 잔차,
  측정 2.514%)다. 줄바꿈 폭은 `06_stack`에 6%(한글↔라틴 경계의 스크립트 간격 잔차, 측정 +5.5% —
  02·03과 같은 원인이고 겹침이 아니다). 나머지 겹침 슬라이드는 기본 2.5%를 넘기지 않는다 —
  예산을 느슨히 두면 순서 갈라짐이 그 그늘에 숨으므로 슬라이드 한정으로만 조인다.
- **도형 안 줄 수의 갈라짐은 오차로 덮지 않고 표로 단정한다** (`inShapeLineDivergences`).
  원인은 여유가 아니라 두 엔진의 **줄바꿈 규칙 차이**다 — Chromium은 한글을 음절 사이에서
  끊고(`데이터와 모델의 편향/을`) LibreOffice는 낱말 경계에서만 끊는다(`데이터와 모델의/편향을
  측정한다`). 그래서 LibreOffice의 첫 줄이 더 짧아지고 밀린 글자가 마지막 줄을 하나 더 만들며,
  **여유가 8.0%인 자리에서도 갈라진다** (폭을 넓혀서는 닫히지 않는다는 증거다). 도형은
  텍스트 박스처럼 넓힐 수도 없다 (박스가 저자가 정한 크기다 —
  [지오메트리 패스](geometry-pass.md)). 갈라진 자리와 줄 수를 표에 적어 두면 나빠질 때도
  **고쳐질 때도** 테스트가 깨진다: 표를 지우는 것이 고쳤다는 증거다.
- **잉크 띠는 잰 줄 박스가 아니라 그림에서 합친다.** 배치가 열리면 한 줄에 박스가 여럿 앉고
  y가 조금씩 엇갈리는데, 줄 박스는 잉크보다 커서 "세로로 겹치는 박스는 한 띠"라는 규칙이
  이웃 줄까지 전이적으로 번진다. 지금은 잰 줄을 **웹 잉크 띠**에 겹침이 가장 큰 쪽으로
  배정하고 양방향으로 검사한다 — 줄마다 잉크가 있어야 하고, 띠마다 주인이 있어야 한다.
- 픽스처는 **병렬로 돌리지 않는다.** 브라우저 세션과 리뷰 갤러리가 공유 상태이고, 병렬
  LibreOffice 프로세스는 CI에서 메모리로 서로를 죽인다. 브라우저는 스위트 전체가 세션 하나를
  공유한다 (`balpyo server`의 웜 세션과 같은 전략).

## 시각 리뷰

`make review`는 테스트와 **같은 코드**를 돌리고 중간 산출물만 남긴다. 테스트가 보는 그림과
사람이 리뷰에서 보는 그림이 다르면 리뷰가 거짓말을 하기 때문이다.

```
review/
├── index.html              # 전체 픽스처 갤러리
└── <픽스처>/
    ├── index.html
    ├── NN-web.png          # 브라우저 스크린샷
    ├── NN-pptx.png         # LibreOffice 렌더
    ├── NN-diff.png         # 다른 픽셀을 마젠타로 강조
    └── <덱>.pptx           # 손으로 열어 볼 산출물
```

`review/`는 커밋하지 않는다 (`.gitignore`). 커밋하는 스냅샷은 픽스처의 `golden/`뿐이다.

**사람이 하는 확인은 갤러리에서 끝나지 않는다.** 각 iteration의 리뷰 단계에서 `deck.pptx`를
macOS Keynote나 PowerPoint로 **직접 열어** 편집 가능성을 확인한다 — 텍스트 박스가 진짜
텍스트 박스인지, 테마 색을 바꾸면 도형 색이 따라오는지. 이 확인은 자동화하지 않는다.
"열리는 파일"과 "편집 가능한 파일"의 차이가 이 제품의 핵심이기 때문이다.

## CI

`.github/workflows/ci.yml`이 **같은 이미지로 같은 `make test`를 돌린다.** 로컬에서 초록이면
CI에서도 초록이어야 하고, 그 등식이 성립하는 이유는 두 곳이 같은 컨테이너를 쓰기 때문이다.
렌더 비교가 실패하면 워크플로우가 `review/` 갤러리를 아티팩트로 올려 실패한 diff 이미지를
받아 볼 수 있게 한다. 문서 빌드(`make docs`, `--strict`)도 같은 워크플로우가 검사한다.
