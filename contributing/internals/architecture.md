# 아키텍처

이 문서는 **지금 저장소에 있는 구조**를 설명한다. 아직 없는 층은 어느 iteration에서
붙는지 표시했다.

## 파이프라인

```
balpyo.json ─┐
             ├→ 설정 (core)
slides/*.slide ─→ 수집 (soml.Collect) ─→ 토크나이즈·파싱 (soml) ─→ 덱 모델
                                                                    │
                                            외관 해석 (core.Resolve) ←┤
assets/** ────────────────→ 에셋 해석 (core.ResolveAssets)           ←┤
                                            검증 (core.Validate)     ←┘
                                                    │
                              ┌─────────────────────┴─────────────────────┐
                              ↓                                           ↓
                    render/web (기준 타깃)              지오메트리 패스 (render/geom)
                    HTML + 생성 CSS + 에셋 파일          좌표 곁 표 → render/pptx → OOXML
                              └─────────────→ 파일 쓰기 (internal/pipeline) ←┘
```

단계마다 지켜지는 성질:

1. **수집은 파일 시스템 순서를 계약으로 바꾼다.** `.slide` 파일만 모으고, 하위 디렉토리는
   챕터, `_` 접두는 무시, 정렬은 경로 세그먼트별 사전순이다. 순서용 숫자 접두(`001_`)는
   정렬에만 쓰이고 딥링크 앵커에서는 떨어진다 — 슬라이드를 재배치해도 링크가 살아남는다.
2. **파싱은 무손실이다.** 토크나이저가 공백·주석·인용 부호를 보존하므로 같은 자료구조를
   `format`과 `lsp`가 재사용한다 ([ADR 0001](../decisions/0001-parser-trivia.md)).
   덱 모델에는 트리비아가 없다 — 렌더러는 의미만 본다.
3. **덱 모델에 도달한 시점에 외관은 확정되어 있고 에셋 바이트도 실려 있다.** 캐스케이드(인라인
   > variant > 컴포넌트 기본값 > 역할·토큰)는 `core.Resolve`가 **한 번만** 적용한다. 렌더러가
   각자 해석하면 웹과 PPTX의 외관이 갈라진다.
4. **렌더러는 순수 함수다.** 덱 모델을 받아 `map[경로]바이트`를 낸다. 디스크 쓰기와 순서
   결정은 파이프라인이 하므로 렌더 테스트가 파일 시스템을 건드리지 않는다 — 그림이 생긴
   뒤에도 그렇다 (파일을 읽는 것은 `core.ResolveAssets` 한 곳이다).
5. **좌표계는 하나다.** 저자·웹 CSS·지오메트리 패스가 모두 논리 스테이지 px를 쓰고, EMU·pt
   변환은 OOXML 경계에서만 일어난다.

## 패키지 경계

| 패키지 | 소유하는 것 | 임포트하지 않는 것 |
|---|---|---|
| `soml/` | 토크나이저, 파서, 덱 모델, 슬라이드 수집, 진단 | 다른 balpyo 패키지 전부 |
| `core/` | `balpyo.json` 설정, 외관 해석, 파일 간 검증 | 렌더러 |
| `render/` | 타깃 계약 (`Target`, `Renderer`, `Files`) | `core` |
| `render/web/` | HTML + 생성 CSS, 요소 식별자 계약 (`ElementID`) | `core`, `render/pptx` |
| `render/geom/` | 지오메트리 패스 — 브라우저 제어(CDP), 좌표 곁 표 | `core`, `render/pptx` (`render/web`은 식별자 계약 때문에 임포트한다) |
| `render/pptx/` | OOXML 조립, 단위 변환(EMU·pt) | `core`, `render/web` |
| `render/quick/` | 내장 렌더러 — 웹 산출물을 브라우저 없이 배치(CSS cascade · flex · grid · 표 · 텍스트)하고 그린다, 측정 JSON | `core`, `render/pptx` (`render/web`은 식별자 계약, `render/geom`은 지오메트리 꼴 때문에 임포트한다) |
| `internal/pipeline/` | 위 층들의 조립, 파일 쓰기 | — |
| `internal/testkit/` | 픽스처 러너, 골든, 렌더 헬퍼, 리뷰 갤러리 | — |
| `internal/snapshot/` | `balpyo snap` — 내장 렌더러의 그림을 PNG · GIF로 쓴다 | — |
| `cmd/balpyo/` | CLI 표면 (플래그 파싱, 출력) | 빌드 로직 |

경계가 이렇게 잡힌 이유:

- **`soml`은 공개 API다.** 덱 모델이 이 제품의 중심이고, 생성기나 에이전트 같은 제3자 도구가
  SOML을 거치지 않고 덱 모델을 만들 수 있어야 한다. 그래서 `soml`은 아무것도 임포트하지 않는다.
- **`core`는 렌더러를 모르고, 렌더러는 `core`를 모른다.** 해석·검증은 타깃과 무관하고, 렌더는
  이미 해석된 모델만 본다. 두 방향의 임포트가 없어야 "외관 해석은 한 곳에서만"이 컴파일러가
  강제하는 규칙이 된다.
- **조립은 `internal/pipeline`이고 `cmd/balpyo`가 아니다.** `main` 패키지는 임포트할 수
  없으므로 CLI에 조립을 두면 테스트 하네스가 같은 흐름을 돌릴 수 없다. 픽스처 스위트와
  `balpyo build`가 **같은 함수**(`pipeline.Build`)를 부르는 것이 "테스트가 검사한 것 = 사용자가
  얻는 것"의 전제다.
- **`internal/`은 공개 API 약속이 없다는 표시다.** 파이프라인과 테스트 하네스는 언제든 모양이
  바뀐다.

## 두 렌더러

### 웹 — 기준 타깃

HTML 파일 하나에 CSS와 뷰어 런타임 JS를 인라인해 낸다 (`index.html`). 외부 의존이 없으므로
어디에 두어도 열린다 — 그림이 있는 덱은 에셋 파일이 함께 나오고(경로는 저자가 쓴 것 그대로),
그 파일들도 산출 디렉토리 안에 있다. 파이프라인이 나중에 복사하는 것이 아니라 **렌더러가
`render.Files`에 담아 내는** 이유는 측정이다: 지오메트리 패스가 재는 것이 이 산출물이고, 그림
바이트가 없으면 브라우저가 깨진 이미지(rect 0×0)를 잰다.

문서는 **두 가지 뷰**를 갖는다 (`render/web/runtime.go`,
[ADR 0006](../decisions/0006-presenter-view-attribute.md)). 사람이 열면 런타임이 <html>에
`data-balpyo-view="presenter"`를 켜서 **발표자 뷰**가 된다 — 슬라이드 한 장이 화면에 맞춰
스케일되고, 하단 가운데 컨트롤 바(이전/다음/카운터/노트 토글)와 키보드·URL 해시 딥링크로
넘긴다. 속성이 없으면(JS 꺼짐, 또는 지오메트리 패스가 지운 상태) **문서 뷰** — 모든
슬라이드가 논리 스테이지 크기 그대로 세로로 쌓인 배치 — 이고, 지오메트리 패스와 스크린샷
하네스가 재는 것은 이쪽이다.

기본 CSS는 **cascade layer**로 `balpyo.base < balpyo.theme < balpyo.author` 순서를 미리
선언한다. 층을 먼저 못 박아 두면 나중에 테마·저자 CSS가 어느 순서로 실려도 우선순위가
뒤집히지 않는다.

슬라이드 요소는 논리 스테이지 크기를 그대로 갖고, `data-slide-index` 같은 속성을 단다.
이 속성은 장식이 아니다 — 지오메트리 패스가 이 선택자로 요소를 집어 좌표를 읽고, 웹 런타임이
딥링크를 여기에 맞춘다.

### PPTX — 네이티브 조립

전략은 두 갈래다.

1. **배치는 브라우저가 정한다** — [지오메트리 패스](geometry-pass.md)가 렌더된 HTML에서
   요소별 rect를 읽어 EMU로 환산한다. 레이아웃 계산을 두 번 구현하지 않는다.
2. **외관은 스키마에서 컴파일한다** — computed style 역추론은 없다. 토큰 색은 리터럴 RGB가
   아니라 `schemeClr` 참조로 나가야 하고(테마 색을 바꾸면 도형이 따라오는 이유), 그것은
   브라우저가 계산한 값에서는 복원할 수 없다.

패키지는 `archive/zip`으로 OPC 패키지를 직조립한다. `[Content_Types].xml`이 첫 엔트리이고,
모든 zip 엔트리의 수정 시각은 1980-01-01로 고정된다 — 빌드 시각이 들어가면 같은 입력이
매번 다른 바이트를 내고 골든 비교가 불가능해진다. 그림이 있는 덱에는 **XML이 아닌 파트**가
들어간다 (`ppt/media/image<N>.<ext>` — 에셋 표의 바이트 그대로).

단위 변환은 `render/pptx/units.go`가 소유한다: `1px = 9525 EMU`, 폰트 `pt = px × 0.75`.
16:9(1280×720)와 4:3(960×720) 모두 이 정수 계수로 PowerPoint 표준 페이지 크기와 정확히
일치한다 ([ADR 0002](../decisions/0002-logical-stage-size.md)).

### 어휘를 늘리면 렌더러 표를 먼저 늘린다

닫힌 어휘의 값은 "쓸 수 있는 것은 그려진다"에 있다. 그래서 어휘는 **네 층에 동시에** 존재해야
한다 — `soml`의 요소 카탈로그(`soml/subset.go`의 `ElementKind`), `core`의 값 해석, 그리고 두
렌더러의 디스패치. 한 층만 열려 있으면 저자는 슬라이드를 다 쓴 뒤에 실패를 만난다.

세 가지가 그 어긋남을 막는다.

| 장치 | 있는 곳 | 하는 일 |
|---|---|---|
| `soml.ElementKinds()` | `soml/subset.go` | 카탈로그의 모든 종류 (상수 선언 순서) |
| `RenderedKinds()` | `render/web`, `render/pptx` | 각 렌더러가 **다루는 종류의 명시 목록** (맵이 아니라 목록 — 대조할 수 있어야 한다) |
| `soml.KindRendered()` | `soml/subset.go` | 아직 어느 렌더러도 그리지 못하는 종류를 **언어 층에 적어 둔 것**(`unrenderedKinds`) |

`render` 패키지의 대조 테스트가 셋을 맞춘다: `KindRendered`가 참인 종류는 두 렌더러 목록에
전부 있어야 하고, 거짓인 종류는 어느 목록에도 없어야 한다. 양방향이라 "렌더러를 빼먹은 것"과
"구현했는데 파서가 계속 막는 것"이 둘 다 실패로 잡힌다. 두 렌더러를 함께 임포트해야 하므로
그 테스트만 `package render_test`다.

그리지 못하는 종류를 쓴 문서는 **파스 시점에** 진단이 난다 — 태그가 있는 자리에서 "is vocabulary that
is not implemented yet"이라고 말하고, 표 하나가 진단 여럿이 되지 않게 가장 바깥 요소에서만
말한다. 렌더 중에 에러로 죽는 길도 막혀 있지만(두 렌더러의 기본 분기), 그 자리까지 오는 것은
파서를 거치지 않은 덱뿐이다.

그래서 태그를 추가하는 순서는 이렇다.

1. `soml`에 종류와 이름·콘텐츠 모델·배치 규칙을 더한다. 렌더러가 아직 없다면 `unrenderedKinds`에
   함께 적는다 — 이 줄이 있으면 파서가 저자에게 즉시 말한다.
2. `core`가 외관을 해석한다.
3. 두 렌더러의 `renderedKinds`를 늘리고 디스패치를 구현한다. **같은 커밋에서
   `unrenderedKinds`의 그 줄을 지운다** — 지우지 않으면 대조 테스트가 실패한다.

## 덱 모델

`soml.Deck`이 렌더러가 보는 유일한 입력이다. 여기 도달한 시점에는 외관이 해석되어 있고
(`core.Resolve`), skip된 슬라이드는 애초에 없다.

| 타입 | 담는 것 |
|---|---|
| `Deck` | 제목·저자·언어, 종횡비, 논리 스테이지, **테마 토큰 표**, 슬라이드 목록 |
| `Slide` | 순번, 딥링크 ID, 원본 경로, 챕터, **레이아웃**(+값 구간), 노트, 콘텐츠 트리, 원문 토큰 열 |
| `Stage` | 논리 스테이지 크기 (px) — 16:9는 1280×720, 4:3은 960×720 |
| `Node` | 콘텐츠 트리 노드 인터페이스 — 구현체는 `Element`와 `Text` |
| `Element` | 태그 이름, 속성(원문 값 + 스팬), 자식, 확정 외관(`Appearance`) |
| `Text` | 공백이 접힌 문자 데이터 |
| `Theme` | 색·폰트 토큰 표 — 순서 있는 목록 (산출물과 진단이 결정적이어야 해서) |
| `Assets` | **에셋 표** — `<image src>`가 가리킨 파일의 키·포맷·고유 크기·바이트 (아래) |
| `Diagnostics` | 에러·경고와 그 위치 (`line:col`) |

### 소유 경계 — 누가 무엇을 해석하는가

한 속성이 세 층을 지나며 역할이 나뉜다. `<text role="title" size="64">`를 예로:

1. **파서(soml)는 이름만 본다.** 태그·속성 이름의 닫힌 어휘와 문법을 검사하고, 값은
   원문 문자열 + 스팬으로 남긴다 (`Attr.Value`/`ValueSpan`). 값의 어휘(역할 5종, 색 토큰)
   는 테마와 함께 자라므로 파서가 알 수 있는 것이 아니다. 예외는 `<slide>`의 `id`·`skip`
   — 외관이 아니라 **구조** 속성이라 값 해석까지 파서가 한다.
2. **core가 값을 해석해 확정한다.** 캐스케이드(인라인 > 역할 기본값 > 테마 토큰)를 한 번
   적용해 `Element.Appearance`(확정 외관)를 채우고, 덱에 `Theme`(토큰 표)를 싣는다.
   값 스팬 덕분에 이 층의 진단도 파서와 같은 정밀도로 line:col을 가리킨다.
3. **렌더러는 확정 값만 읽는다.** `Attrs`를 다시 해석하지 않는다 — 렌더러가 각자 해석하면
   웹과 PPTX의 외관이 조용히 갈라지고, 그 버그는 두 산출물을 나란히 보기 전까지 드러나지
   않는다.

### 슬라이드 수준 속성이 렌더러에 닿는 경로

대부분의 슬라이드 속성은 렌더러 앞에서 소진된다 — `id`는 딥링크 앵커로, `skip`은 덱에서
빠지는 판정으로, `note`는 노트 슬라이드로 간다. `layout`(Iteration 6)은 다르다: **배치를
바꾸는 첫 슬라이드 속성**이라 렌더러까지 값으로 도달해야 한다. 경로는
`SlideDoc.Layout`(파서가 남긴 원문) → `Slide.Layout`(파이프라인이 옮긴다) →
`core.Resolve`(2종 어휘를 확정) → 렌더러(`writeStage`가 `content`/`canvas`를 읽어 스테이지
CSS를 고른다)다.

- **렌더러는 문자열이 아니라 `soml.SlideLayout` 타입을 소비한다** — `"canvas"` 리터럴이 세
  렌더러에 흩어지면 오타 하나가 한 타깃에서만 배치를 바꾼다. 어휘 확정을 core가 한 번만 하는
  것은 외관 캐스케이드를 한 곳에서만 하는 것과 같은 근거다.
- **값과 함께 구간(`Slide.LayoutSpan`)을 싣는다.** `layout`의 어휘 검사는 값 층(core)의
  몫인데(레이아웃 어휘는 테마와 함께 자란다 — Iteration 10), 그 진단이 `line:col`을 가리키려면
  값의 소스 위치가 필요하다. 덱 모델에는 파서 트리가 없으므로(해석이 끝난 값이다) `Slide`가
  값과 구간을 함께 나른다 — 어휘 밖 `layout="titel"`이 부호가 아니라 값에 밑줄을 긋는 이유다.
- 버린 선택지: **`Slide`에 루트 요소 참조를 싣는 것**. 그러면 구간을 따로 나를 필요가 없지만
  덱 모델이 "해석이 끝난 값"이라는 성질이 깨지고, 렌더러가 원문 트리를 다시 읽을 수 있게 되어
  "렌더러는 확정 값만 본다"는 경계가 흐려진다. 값 하나에 구간 하나를 붙이는 편이 싸다.

### 외관이 붙는 자리

확정 외관은 요소에 붙는다 (`Element.Appearance` → `TextStyle`). 색은 토큰 참조와 리터럴을
구분해 담고(`soml.Color`), **토큰은 렌더러 경계까지 이름으로 남는다** — 웹은
`var(--balpyo-color-*)`, PPTX는 `a:schemeClr` 참조로 눕혀서 내보낸 파일이 테마 편집을
따라간다 ([외관 속성](../../docs/reference/appearance.md)). 두 렌더러의 색·폰트가 덱에 실린
**한 표**(`Deck.Theme`)에서 나오는 것이 두 타깃이 같은 색을 내는 구조적 이유다.

### 에셋 표 — 값이 디스크를 가리키는 자리

`<image src>`가 가리킨 파일은 **덱의 에셋 표**(`Deck.Assets`)를 지나 렌더러에 도달한다. 표의 항목
하나가 파일 하나다:

| 필드 | 담는 것 | 누가 채우는가 | 누가 읽는가 |
|---|---|---|---|
| `Key` | 프로젝트 루트 기준 정규화 경로 (`assets/wide.png`) | `core.ResolveAssets` | 웹(산출 파일 이름·`<img src>`), PPTX(파트 조회) |
| `Format` | **내용이 판정한** 포맷 (`png`·`jpeg`) | 같음 | PPTX (`[Content_Types]`의 `Default`, 미디어 파트 확장자) |
| `Width`·`Height` | 고유 크기 (논리 스테이지 px 그대로) | 같음 | PPTX (`cover` 크롭 비율 계산) |
| `Bytes` | 파일 내용 **그대로** (리사이즈·재압축·EXIF 회전 없음) | 같음 | 웹(산출 파일), PPTX(`ppt/media/*`) |

- 표는 **참조에서 만들어진다** — 순서는 첫 사용의 문서 순서이고, 같은 키는 한 항목이다.
  그 순서가 PPTX 미디어 파트 번호의 근거이므로 맵이 아니라 순서 있는 목록이다 (`Deck.Theme`과
  같은 태도).
- **채우는 시점이 `core.Resolve`와 `core.Validate` 사이다.** 파일 시스템을 받는 별도 진입점
  (`core.ResolveAssets(deck, fs.FS)`)인 이유는 값 층이 둘로 나뉘기 때문이다: 경로 **문법**은
  `Resolve`가 디스크 없이 보고(에디터가 프로젝트를 열지 않고도 진단한다), 파일이 실제로 무엇인지
  (존재·디렉토리 여부·헤더·고유 크기)는 이쪽이 본다.
- **왜 지오메트리와 달리 덱에 있는가.** 측정값을 곁 표로 뺀 두 근거가 여기서는 성립하지 않는다:
  에셋은 파생 데이터가 아니라 **입력**이고, 렌더 전에 결정적으로 한 번 채워지므로
  `--target html,pptx`와 `pptx,html`이 같은 덱을 본다 — "렌더러는 순수 함수"가 깨지지 않는다.
  이미 같은 성질의 표가 덱에 있다: `Theme`이다 (core가 채우고 두 렌더러가 읽는다). 결정 전체는
  [ADR 0023](../decisions/0023-assets-live-in-the-deck.md)에 있다.
- **고유 크기는 표에만 있다.** 확정 외관(`soml.ImageStyle`)은 어느 에셋인가(`Src`)만 담는다 —
  같은 그림을 두 번 쓴 슬라이드에서 두 확정 값이 자기 크기를 다르게 말할 수 있게 되면 같은
  사실이 두 벌이 된다.

### 지오메트리가 덱이 아니라 곁 표인 이유

브라우저가 잰 좌표는 덱 모델에 싣지 않고 별도 타입(`geom.Geometry`)으로 PPTX 렌더러
생성자에 주입한다. 덱은 공개 계약이고, 덱에 실으면 값이 채워지는 시점이 `--target` 순서에
의존해 "렌더러는 순수 함수"라는 성질이 깨진다 —
[ADR 0004](../decisions/0004-geometry-side-table.md)와
[지오메트리 패스](geometry-pass.md) 참조.

## 진단

진단은 한 곳에서 나온다. 파일 하나 안에서 볼 수 있는 것(닫힌 어휘, 문법)은 파서가, 파일을
넘어야 알 수 있는 것(슬라이드 ID 충돌, 나중의 `<arrow from>` id 참조·슬롯 이름)은
`core.Validate`가 진단한다. `build`·`check`·`lsp`가 같은 함수를 공유하므로 **에디터에서 본
진단과 CI가 막는 진단이 같다.**

`--strict`는 경고를 에러로 승격한다. 경고는 빌드가 실패한 경우에도 사람에게 출력된다.
