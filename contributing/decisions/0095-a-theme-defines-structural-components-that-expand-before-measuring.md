# 0095 — 테마는 구조 컴포넌트를 정의하고, 컴포넌트는 측정 전에 기존 어휘로 펼쳐진다

- 상태: 확정 (파서 단계 구현 — 펼침 · 테마 로드 · 문서는 이어서)
- 날짜: 2026-11-25
- 관련: [ADR 0059](0059-chart-is-desugared-into-shapes-and-text-not-a-native-chart-part.md)(`<chart>`는 도형과 텍스트로 펼쳐진다), [ADR 0091](0091-a-theme-carries-a-readme-for-the-deck-author.md)(테마 README),
  이슈 #130

## 맥락

테마가 정의할 수 있는 것은 외관(variant · componentDefaults), 배치(고정된 11개 레이아웃과 슬롯), 그림
(`theme:`)이다. 디자인 시스템이 정한 **반복 구성 단위** — "아이콘 타일 + 라벨 + 설명"인 단계 하나, "마커 +
연도 태그 + 설명"인 타임라인의 한 시점 — 는 테마가 담을 자리가 없어 README의 마크업 레시피가 되고, 덱
저자가 장마다 복사한다. 구조가 원고에 복제되면 테마를 바꿔도 원고가 그대로라는 약속이 외관에서 멈추고,
원고에는 "타임라인의 한 시점"이 아니라 도형 다섯 개가 남는다.

질문은 넷이다: **사용처를 어떻게 쓰는가**, **정의에 무엇을 허용하는가**, **어휘를 언제 · 누가 아는가**,
**언제 펼치는가**.

## 선택지

**(1) 사용처의 문법**

- (가) `<use component="step" icon="…">` — 어휘에 태그 하나만 더한다.
- (나) **정의된 이름이 곧 태그다** (`<step icon="…">`).

**(2) 정의의 표현력**

- (가) 반복 · 조건 · 식을 담은 템플릿 언어.
- (나) **치환과 자식 삽입만** — `{name}` 자리와 `<slot/>` 하나.

**(3) 어휘의 검사 시점**

- (가) 파서는 모르는 태그를 통과시키고 값 층(core)이 테마를 본 뒤 거른다.
- (나) **파서가 컴포넌트 어휘를 받는다** (`soml.ParseWith`). 테마를 읽는 것은 호출자다.

**(4) 펼치는 시점**

- (가) 렌더러가 컴포넌트를 안다.
- (나) **`core.Resolve` 앞에서 기존 어휘의 노드로 펼친다** — 측정 · 배치 검사 · PPTX 매핑은 새 종류를 모른다.

## 결정

1. **(1)은 (나)다.** 정의 파일은 `components/` 아래의 `.slide`이고 루트가 `<define name params>`다. 이름은
   소문자 케밥 낱말이고 내장 태그와 겹칠 수 없다.
2. **(2)는 (나)다.** `params="icon label note?"` — `?`로 끝난 인자는 생략할 수 있다(빈 문자열로 치환). 인자
   자리는 속성 값과 글자 안의 `{name}`이고, 이름 문법에 맞지 않는 중괄호는 글자 그대로다. `<slot/>`은 정의에
   하나까지이고 사용처의 자식이 그 자리에 들어간다. 다른 컴포넌트를 쓰는 정의는 아직 받지 않는다(한 겹이면
   순환이 없다). 이름 붙은 슬롯과 자식 번호에 따른 변형은 이 ADR의 범위 밖이다.
3. **(3)은 (나)다.** 정의 몸체는 슬라이드와 같은 닫힌 어휘로 파싱한다. 사용처는 **펼친 모양으로** 판정한다 —
   `<step>`은 정의 뿌리가 놓일 수 있는 자리에 놓이고, 그 자식은 `<slot/>`을 담은 요소의 문법을 따른다.
   사용처 속성은 인자에, 뿌리가 받는 배치 속성(`grow` · `slot` · `enter` …)을 더한 것이다(배치 속성과 같은
   이름의 인자는 에러). 빠진 필수 인자 · 모르는 인자 · 모르는 `{name}`은 파스 진단이다. 컴포넌트 어휘 없이
   파싱하면 같은 태그는 지금처럼 모르는 태그다.
4. **(4)는 (나)다.** 펼친 노드는 사용처를 기억해 값 층의 진단이 사용처와 정의 위치를 함께 말한다.
5. **상속과 폴백.** 자식 테마는 부모의 컴포넌트를 물려받고 같은 이름을 다시 정의하면 통째로 대체한다
   (variant · 레이아웃과 같은 규칙). 폴백 테마는 없다 — 덱이 쓰는 컴포넌트를 테마가 정의하지 않으면 빌드가
   에러로 멈춘다.

## 근거

**왜 이름이 곧 태그인가.** 원고에 남아야 하는 것은 의미다. `<use component="step">`은 의미를 속성 값으로
밀어 넣어 원고를 길게 하고, 이름 오타를 값 진단으로 만든다. 이름이 태그면 오타가 지금의 "모르는 태그"
진단 — 후보 제안까지 — 을 그대로 받는다.

**왜 치환만인가.** 테마는 데이터만 담고 코드를 돌리지 않는다. 반복은 사용처가 자식을 여러 개 적는 것으로
충분하고, 조건이 필요해 보이는 자리(타임라인의 위 · 아래 교대)는 사용처의 속성 하나로 풀린다.

**왜 파서가 어휘를 받는가.** 닫힌 어휘의 진단은 파스 시점에 `line:col`과 함께 나오는 것이 계약이다(파서 ·
`core.Validate` 두 곳에서만). 모르는 태그를 값 층까지 통과시키면 파서의 자리 · 자식 · 공백 규칙이 그 아래에서
모두 꺼진다. 테마 이름은 설정에서 이미 알고 있으므로 파싱 전에 컴포넌트 어휘를 읽는 데 드는 것은 순서뿐이다.

**왜 펼친 모양으로 판정하는가.** 펼친 트리가 같은 파서 규칙을 다시 통과해야 렌더러가 새 종류를 몰라도 된다.
사용처 검사를 정의에서 파생하면 정의가 바뀔 때 사용처 규칙이 따로 낡지 않는다.

## 결과

- `soml`에 `ParseComponent` · `ParseWith` · `Components`가 생긴다 (공개 API).
- 남은 일: 테마 · 프로젝트의 `components/` 로드와 `extends` 병합, 파이프라인의 순서 변경(어휘 → 파싱), 펼침과
  사용처를 기억하는 진단, `balpyo theme info`의 컴포넌트 목록, 레퍼런스 문서와 덱 스킬.
