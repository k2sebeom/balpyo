# 0075 — 설치한 테마는 `~/.balpyo`에 사는 **이름**이고, 그 이름은 테마가 정한다

- 상태: 확정 (0054의 "열지 않은 것" 중 원격 테마 설치를 연다)
- 날짜: 2026-10-09
- 관련: [ADR 0054](0054-an-external-theme-is-a-name-inside-the-project-and-extends-overrides-by-name.md)(외부
  테마는 프로젝트 안의 이름이다), [ADR 0067](0067-prd-is-retired-and-its-standing-decisions-move-here.md)(테마는
  JS를 담지 않는다), [테마 패키지](../../docs/reference/theme.md), [CLI](../../docs/reference/cli.md)

## 맥락

ADR 0054는 테마를 **이름**으로 고정하고 그 이름을 찾는 자리를 둘로 열었다 — 내장 테마와
`<프로젝트>/themes/<이름>/`. 팀이 테마를 나누는 길은 그 디렉토리를 복사하는 것뿐이었고, 원격 테마
설치(`theme get`)는 "열지 않은 것"으로 남았다. 회사 테마를 GitHub 저장소 하나로 관리하면 덱마다 그
디렉토리를 복사하고, 테마가 고쳐질 때마다 다시 복사해야 한다.

받아들일 조건은 0054가 이미 정했다: `balpyo.json`의 `theme`는 이름 하나이고 경로 문법은 없다.
그러니 질문은 **어디에서 받아 어디에 두고, 어떤 이름으로 부르는가**다. 그리고 실제 테마 저장소는
테마를 하나만 담지 않는다 — `acme`와 그것을 상속한 `acme-dark`가 한 저장소에 있고, 이 저장소처럼
테마 디렉토리가 여러 깊이에 흩어진 경우도 있다(`core/themes/*`, `examples/themes/*`,
`testdata/fixtures/*/themes/*`).

## 선택지

**(1) 설정이 원격 테마를 가리키는 방법**

- (가) `theme`에 GitHub URL을 쓴다 — 빌드가 받아 캐시한다.
- (나) **`theme`는 이름 그대로 두고, 설치는 별도 명령**(`balpyo theme install <GitHub URL>`)이 한다.

**(2) 설치한 테마를 두는 자리**

- (가) 프로젝트의 `themes/<이름>/`에 복사한다 (벤더링).
- (나) `~/.cache/balpyo/…`.
- (다) **`~/.balpyo/themes/<이름>/`** — `BALPYO_HOME`으로 바꿀 수 있다.

**(3) 설치한 테마의 이름**

- (가) 저장소 이름이나 디렉토리 이름.
- (나) **`theme.json`의 `name`** — 테마가 자기 이름을 정한다.

**(4) 한 저장소에 테마가 여럿일 때**

- (가) 테마는 저장소 루트에 하나만 있어야 한다.
- (나) 여럿이면 저자가 반드시 하나를 고른다.
- (다) **`theme.json`이 있는 디렉토리를 모두 후보로 찾는다. 이름을 주지 않으면 전부, 주면 그것과
  같은 저장소 안의 `extends` 부모를 설치한다.**

**(5) 다른 기계·CI에서 덱이 요청한 테마가 없을 때**

- (가) 프로젝트에 잠금 파일(`balpyo.lock`)을 두고 빌드나 설치가 그것으로 복원한다.
- (나) **이름을 모른다는 에러로 멈춘다** — 받을 URL은 사람이 안다.

**(6) 설치한 테마와 프로젝트 로컬 테마의 이름이 같을 때**

- (가) 0054처럼 프로젝트를 열자마자 에러.
- (나) 로컬이 이긴다.
- (다) **그 이름이 요청될 때만 에러** (`theme`·`--theme`·`extends` 체인에 나올 때).

## 결정

1. **(1)은 (나)다.** `theme`는 여전히 이름이다. 설치는 `balpyo theme install <GitHub URL> [이름…]`이
   하고, 빌드는 네트워크를 쓰지 않는다. 명령은 `install`·`list`·`remove`·`update` 넷이다.
2. **(2)는 (다)다.** 설치한 테마는 `~/.balpyo/themes/<이름>/`에 놓인다 — 내장 테마(`themes/<이름>/` 임베드)·
   프로젝트(`themes/<이름>/`)와 **같은 구조**라 로더가 세 번째 자리를 같은 코드로 읽는다. 출처(저장소·
   하위 경로·ref·커밋)는 `~/.balpyo/themes.json`에 적는다. `BALPYO_HOME`이 있으면 `~/.balpyo` 대신 그
   디렉토리다.
3. **이름을 찾는 자리는 셋이다: 내장 ∪ 프로젝트 `themes/` ∪ 설치한 테마.** `extends`도 같은 어휘로
   부모를 찾는다.
4. **(3)은 (나)다.** 설치할 때 `theme.json`의 `name`을 읽고 그 이름의 디렉토리에 둔다. 그래서 0054의
   "디렉토리 이름과 `name`이 같아야 한다"는 설치한 테마에서도 그대로 성립한다 — 저장소 안의 디렉토리
   이름은 상관없다.
5. **(4)는 (다)다.** 받은 저장소(또는 URL이 가리킨 하위 경로)를 훑어 `theme.json`이 있는 디렉토리를
   후보로 삼는다. `.`으로 시작하는 디렉토리는 보지 않고, 테마 디렉토리 안으로는 더 내려가지 않는다.
   - 이름을 주지 않으면 후보 전부를 설치한다.
   - 이름을 주면 그 테마와, `extends`가 가리키는 부모 중 **같은 저장소에 있는 것**을 함께 설치한다.
   - 설치하려는 이름이 저장소 안에서 두 번 나오면 에러다 (두 경로를 함께 적는다).
6. **설치는 전부 되거나 전부 안 된다.** 임시 디렉토리에 풀고, 옮긴 뒤 설치한 테마를 빌드와 같은
   로더로 **전부 로드해** 검사하고(완전성·`extends` 체인), 하나라도 실패하면 원래 상태로 되돌린다.
   다음은 설치 에러다: 내장 테마와 같은 이름, 다른 출처에서 이미 설치한 이름(`--force`로 교체),
   테마 디렉토리 안의 심볼릭 링크, 압축 안에서 위로 나가는 경로.
7. **(5)는 (나)다.** 요청한 이름이 어휘에 없으면 "알 수 없는 테마"로 멈추고 세 자리 어디에도 없다고
   말한다. 잠금 파일은 두지 않는다.
8. **(6)은 (다)다.** 프로젝트 `themes/acme/`와 설치한 `acme`가 함께 있어도 그 이름을 요청하지 않는
   덱은 빌드된다. 요청하면 에러이고, 진단이 고치는 두 길(로컬 테마의 이름을 바꾸기, 설치를 지우기)을
   적는다. 내장 이름과 겹치는 로컬 테마는 0054대로 프로젝트를 열자마자 에러다.
9. **설치한 테마의 배치 CSS 검사(lint)는 빌드에서 돌지 않는다** — 내장 테마와 같다. 그 경고는 덱
   저자가 고칠 수 없는 파일을 가리키고, `--strict` 빌드를 남의 파일로 막는다. 같은 검사는 **설치할 때**
   돌고 경고로 나온다.
10. **열지 않은 것**: 비공개 저장소(인증), GitHub 밖의 호스트, 잠금 파일, 버전 범위, 다른 저장소에 있는
    `extends` 부모의 자동 설치(이미 설치되어 있으면 쓴다), 프로젝트 안 설치.

## 근거

**왜 설정이 URL을 받지 않는가.** 0054의 근거가 그대로다: 값의 종류가 둘이 되면 진단이 두 어휘를
설명해야 한다. 더해서 URL을 받는 순간 빌드가 네트워크에 매인다 — 오프라인에서 멈추고, 같은
`balpyo.json`이 ref가 움직이면 다른 바이트를 낸다. 설치를 명령으로 떼면 빌드는 지금처럼 디스크만
읽고, 네트워크를 쓰는 자리는 사람이 친 명령 하나다.

**왜 `~/.balpyo`인가.** 테마는 한 사람의 여러 덱이 함께 쓰는 것이라 프로젝트마다 복사하면 0054 이전의
문제(덱마다 복사본)로 돌아간다. 캐시 디렉토리(`~/.cache`)가 아닌 이유는 그 자리가 "지워도 되는 것"을
뜻한다는 것이다 — 설치한 테마를 지우면 덱이 빌드되지 않는다. 사람이 찾아 열 수 있는 이름이어야 하고,
`~/.balpyo/themes/<이름>/`은 이미 아는 모양이다 (내장·프로젝트와 같은 구조).

**왜 이름을 테마가 정하는가.** 덱이 부르는 것은 이름이고, 그 이름이 저장소 이름에 매이면 한 저장소의
테마 여럿이 부를 이름을 갖지 못한다. `theme.json`의 `name`은 0054가 "언젠가 패키지 안에 자기 이름을
들고 있어야 한다"며 남긴 필드이고, 지금 그 쓰임이 온다. 설치가 그 이름을 디렉토리 이름으로 쓰므로
0054의 같음 검사가 잠금으로 계속 일한다.

**왜 여러 테마를 전부 설치하는가.** 저장소는 배포 단위다 — `acme-dark`가 `acme`를 상속하면 둘은 함께
움직인다. 이름을 주면 같은 저장소의 부모를 따라 설치하는 것도 같은 이유다: 부모 없이 설치한 자식은
로드되지 않는다. 고르지 않으면 실패하는 규칙(4)(나)은 테마가 하나인 흔한 저장소에서도 같은 질문을
던지게 만든다. 반대로 이 저장소처럼 내장 이름과 겹치는 테마를 담은 저장소는 전부 설치가 에러가 되고,
그 진단이 이름을 골라 다시 치라고 말한다.

**왜 잠금 파일이 없는가.** `balpyo.json`이 이름만 담는 한 빌드는 받을 곳을 모르고, 받을 곳을 설정에
적는 순간 (1)(가)로 돌아간다. 처음 보는 기계에서 필요한 것은 무엇이 없는지 아는 것이고, 그 에러가
충분히 정확하면(세 자리 어디에도 없다) 사람이 URL을 안다.

**왜 겹침이 요청될 때만 에러인가.** 0054가 로컬과 내장의 겹침을 프로젝트 전체의 에러로 둔 이유는 둘
다 **이 프로젝트의 사실**이라는 것이다. 설치한 테마는 기계의 사실이다 — 홈에 무엇을 설치했는지가
상관없는 프로젝트의 빌드를 깨면, 에러가 고칠 자리에서 멀어진다. 그 이름을 요청하는 순간에는 "어느
쪽인가"라는 답할 수 없는 질문이 실제로 생기므로 거기서 멈춘다.

## 결과

- **`core`**: `WithInstalledThemes(project, home fs.FS)`가 프로젝트 파일 시스템에 설치한 테마를 붙인다
  (`Resolve`·`ResolveAssets`·수집은 같은 값을 받는다). `LoadConfigWithThemes(projectDir, home)`가 설치한 테마를
  아는 어휘로 이름을 검사한다. `ThemeNames`·진단의 목록이 세 자리를 합친다. 설치 쪽이 쓰는
  `ReadThemeHeader`·`CheckInstalledTheme`가 공개된다.
- **`internal/themestore`**: 홈의 위치, GitHub tarball 받기(`codeload.github.com`, `git` 불필요), 후보
  찾기, 원자적 설치·되돌리기, `themes.json`, `list`·`remove`·`update`.
- **`internal/pipeline`**: `Options.ThemeHome` — 비면 설치한 테마를 보지 않는다(테스트가 개발자의 홈에
  매이지 않는다). CLI가 `BALPYO_HOME` 또는 `~/.balpyo`를 넣는다.
- **`cmd/balpyo`**: `balpyo theme install|list|remove|update`. `build`·`check`·`watch`·`preview`가 설치한
  테마를 본다.
- **문서**: `reference/cli.md`(`balpyo theme`), `reference/theme.md`(설치한 테마 절·새 에러),
  `guides/theming.md`(테마 나누기).
