# 0062 — 뷰어 런타임은 **embed된 자산**이고, 오버뷰와 인쇄는 **뷰의 상태**다

- 상태: 확정
- 날짜: 2026-09-21
- 마일스톤: P6 (배포 — 웹 런타임 마감)
- 관련: [ADR 0006](0006-presenter-view-attribute.md)(발표자 뷰는 `<html>`의 속성 하나다),
  [ADR 0021](0021-measure-view-disables-transforms.md)(측정 뷰에서 변형을 끈다),
  [ADR 0047](0047-review-gallery-lives-in-internal-preview.md), PRD §9.1(웹 런타임),
  PRD §9.5(PDF 렌더러), [SOML — slide](../../docs/reference/soml/slide.md),
  [지오메트리 패스](../internals/geometry-pass.md)

## 맥락

P6의 마지막 항목은 "웹 런타임 마감(오버뷰·`reveal`·인쇄)"이다. 이 결정은 그중 **뷰어 쪽 둘**
(오버뷰·인쇄)과 **런타임 코드가 사는 자리**를 정한다. `reveal`은 언어(속성 어휘)를 늘리므로
별도 결정으로 뺀다.

ADR 0006이 남긴 계약이 이 결정의 출발점이다: 뷰 전환은 `<html>`의 `data-balpyo-view` 하나이고,
그 값이 없으면 **문서 뷰**(모든 슬라이드를 논리 스테이지 크기로 세로로 쌓은 것 — 지오메트리
패스와 픽셀 게이트가 재는 배치)다. 지금 값은 둘이다: `presenter`, `measure`.

### 실측 — 지금 인쇄하면 무엇이 나오나

10장 덱(`examples/incident-postmortem`)을 브라우저에서 열고 그대로 인쇄했다
(CDP `Page.printToPDF`, `preferCSSPageSize`):

| 인쇄 시점의 뷰 | 결과 |
| --- | --- |
| `presenter` (사용자가 파일을 열면 이 상태다) | **1페이지** · 612×792pt(letter) — 활성 슬라이드 하나만, 컨트롤 바까지 |
| 문서 뷰(속성 지움) | **6페이지** · letter — 10장이 페이지 경계에서 **잘려** 두 페이지에 걸친다 |

즉 지금의 산출물은 "인쇄"라는 경로에서 **덱이 아니다**. 발표 중에 `Cmd+P`를 누르는 사람이 받는
것은 지금 화면 한 장이고, 그 실패는 조용하다 (PDF는 정상적으로 나온다).

후보 CSS(`@media print` + `@page { size: <스테이지>; margin: 0 }` + 슬라이드마다 `break-after`)를
같은 페이지에 주입해 다시 인쇄했다 — **발표자 뷰가 켜진 상태에서**:

```
Pages:      10
Page size:  960 x 540 pts        # = 1280×720px @96dpi, 여백 0
```

한 장이 한 페이지고, 세 번째 페이지를 PNG로 뽑아 눈으로 확인했다 (타임라인 슬라이드가 온전히,
꽉 차게 들어 있었다). `size`를 `13.3333in 7.5in`으로 준 것과 `1280px 720px`으로 준 것은
**바이트까지 같은 PDF**였다.

### 실측 — 오버뷰는 `zoom`이고 `transform`이 아니다

오버뷰는 슬라이드 전부를 격자로 줄여 놓고 하나를 골라 들어가는 화면이다. 줄이는 수단이 둘인데,
레이아웃에 미치는 영향이 다르다:

| 수단 | 슬라이드의 레이아웃 크기 | 부모(격자)가 보는 크기 |
| --- | --- | --- |
| `transform: scale(0.22)` | 1280×720 | **1280×720** — 격자 칸이 줄지 않는다 |
| `zoom: 0.22` | 1280×720 (`offsetWidth`) | **282×158** (`getBoundingClientRect`) |

`zoom`을 쓴 격자는 10장이 5열로 흘렀고(덱 높이 381px), 스크린샷으로 확인했다 — 장마다 표·차트·
코드까지 알아볼 수 있었다. 중요한 부수 사실 하나: `zoom` 아래에서도 `offsetWidth`는 논리
스테이지 그대로였다. 런타임이 화면 맞춤 배율을 그 값으로 계산하므로(`runtimeJS.fit`), 오버뷰를
드나드는 것이 배율 계산에 되먹임을 만들지 않는다.

`transform`으로 격자를 만들려면 타일마다 **감싸는 요소**가 필요하다. 그 요소는 지오메트리 패스가
읽는 DOM(슬라이드의 부모 사슬)을 바꾸므로, 발표 기능 하나가 측정 경로를 건드리게 된다.

### 실측 — 인라인 자산의 크기와 그 자리의 제약

10장 덱의 `index.html`은 54,002바이트이고 그 안에서 `<style>` 10,998 · `<script>` 3,959이다
(런타임 JS는 PRD의 ~10KB 목표 안에 있다). 그러나 그 JS는 지금 **Go의 backtick 문자열** 안에
있어서, 백틱을 한 글자도 쓸 수 없다 — 즉 JS 템플릿 리터럴을 쓸 수 없고, 에디터·린터·문법
검사는 그 문자열 안을 들여다보지 않는다. 오버뷰와 `reveal`이 들어오면 이 파일은 지금의 두 배가
된다.

## 선택지

1. **런타임을 Go 문자열로 계속 둔다** — 지금 그대로. 늘어난다.
2. **`go:embed`로 자산 파일로 뺀다** (`runtime.js`·`viewer.css`) — 전달 방식은 그대로(인라인).
3. **번들러를 들인다** (TS + esbuild) — PRD가 말한 "vanilla TS, 빌드 산출물을 내장".

오버뷰의 자리도 셋이다: (a) 네 번째 뷰 값, (b) 발표자 뷰 안의 클래스, (c) 별도 페이지.

## 결정

1. **런타임 자산은 `go:embed`로 파일이 된다** (선택지 2): `render/web/assets/runtime.js`와
   `render/web/assets/viewer.css`. **전달 방식은 바뀌지 않는다** — 여전히 `index.html` 안에
   인라인되고 외부 참조는 없다 (파일로 열어도 도는 계약, PRD §9.1). 번들러(선택지 3)는 열지
   않는다: 지금 런타임은 4KB의 vanilla JS이고, 번들러는 "환경은 하나"(컨테이너 + make)에
   두 번째 툴체인을 들인다 — 근거가 생기는 자리는 런타임이 모듈로 갈라질 때다.
2. **인라인의 안전 조건을 테스트가 판정한다**: 자산은 `</script>`도 `<!--`도 담지 않는다
   (담으면 스크립트가 거기서 끝나 문서가 깨진다). 이것은 문자열이 파일로 나가면서 사람의 눈
   밖으로 나가는 유일한 위험이므로 게이트에 둔다.
3. **오버뷰는 네 번째 뷰 값이다** (선택지 a): `data-balpyo-view="overview"`. 뷰 전환의 구현이
   하나면 측정·발표·오버뷰가 같은 파일을 보면서도 각자에게 맞는 배치를 본다 (ADR 0006).
4. **오버뷰는 `zoom`으로 줄인다**. 감싸는 요소를 만들지 않는다 — 발표 기능이 측정 경로의 DOM을
   바꾸지 않는다 (위 실측).
5. **오버뷰에서 나가는 길은 둘이다**: 타일을 클릭하면 **그 슬라이드**로 들어가고, `Esc`나 `o`를
   다시 누르면 **보고 있던 슬라이드**로 돌아온다 (오버뷰는 이동이 아니라 보기다 — 들어갔다
   나오는 것으로 현재 슬라이드가 바뀌면 발표 중에 자리를 잃는다).
6. **인쇄는 문서 뷰의 그림이다.** `@media print`가 **어느 뷰에서든** 세로 스택·스케일 없음·
   크롬 없음으로 되돌리고, `@page { size: <논리 스테이지>px; margin: 0 }`으로 한 장이 한 페이지가
   된다. 사람이 `Cmd+P`를 누르는 시점은 발표자 뷰이므로, 인쇄 규칙은 `balpyo.base` 층의
   **마지막**에 온다 (같은 명시도면 뒤가 이긴다 — `!important`는 그것으로 부족한 자리에만 쓴다).
7. **인쇄는 브라우저의 것이고 명령이 아니다.** `balpyo pdf`를 열지 않는다 — PRD §9.5의 PDF
   렌더러는 헤드리스 브라우저로 이 CSS를 인쇄하는 일이므로, **이 CSS가 그 명령의 전제**다. 지금
   여는 것은 전제뿐이고, 명령은 노트 포함 옵션·슬라이드 범위와 함께 따로 결정한다.
8. **인쇄를 판정하는 테스트는 실제로 인쇄한다**: `geom.Session.Print`(CDP `printToPDF`)를 열고,
   나온 PDF를 이미 있는 도구(`pdftoppm`)로 펼쳐 **페이지 수 = 슬라이드 수**, 페이지 비율 =
   스테이지 비율, 그리고 페이지마다 잉크가 있다(빈 페이지가 아니다)를 본다. 픽셀 대조까지는
   하지 않는다 — 인쇄는 같은 CSS의 다른 미디어이므로 게이트의 무게는 "덱이 온전히 나왔다"에 둔다.

## 근거

- **뷰 값 하나로 미는 근거는 ADR 0006의 결과다.** 발표자 뷰가 속성 하나였기 때문에 지오메트리
  패스가 "속성을 지운다" 한 줄로 측정 배치를 얻었고, 측정 뷰(ADR 0021)가 세 번째 값으로 들어올
  때 추가 기계가 필요하지 않았다. 오버뷰도 같은 자리에 들어가면 `balpyo server`의 발표자 뷰와
  `balpyo preview`의 갤러리가 전부 같은 계약을 계속 쓴다.
- **`zoom`을 고르는 근거는 측정 경로의 불변성이다.** 발표 기능을 위해 DOM에 요소를 하나 더하면
  지오메트리 패스가 읽는 부모 사슬이 달라진다 — 그 위험은 "오버뷰가 예쁘다"로 상쇄되지 않는다.
- **인쇄를 뷰가 아니라 미디어로 두는 근거는 사용자의 동작이다.** 인쇄는 사용자가 뷰를 바꾸고 나서
  하는 일이 아니라 **지금 보고 있는 화면에서** 누르는 것이다. 그러므로 뷰 값 하나를 더 만들어
  "인쇄 뷰로 바꾼 뒤 인쇄하라"고 요구하면, 요구를 모르는 사람이 잘린 PDF를 받는다 (지금이 그렇다).
- **embed의 근거는 크기가 아니라 도구다.** 4KB가 문제가 아니라, 그 4KB가 Go 문자열이라 백틱을
  못 쓰고 문법 검사도 못 받는다는 것이 문제다. 자산 파일로 나가면 에디터와 사람이 그것을 JS로
  읽는다 — 그리고 `core/theme_package.go`·`internal/scaffold`가 이미 같은 방식으로 자산을 싣는다
  (새 패턴이 아니다).

## 결과

**열리는 것**

- `o`/`Esc`와 컨트롤 바 버튼으로 오버뷰를 드나든다. 타일 클릭으로 슬라이드를 고른다.
- 어느 뷰에서든 `Cmd+P`가 **한 장 = 한 페이지**의 PDF를 낸다 (여백 0, 크롬 없음).
- 런타임이 `render/web/assets/`의 JS·CSS 파일이 된다 — 다음 항목(`reveal`)이 그 파일에서 자란다.

**닫히는 것 (근거가 생기면 다시 연다)**

- **`balpyo pdf` 명령** — 이 CSS가 전제다. 노트 포함·슬라이드 범위·폰트 임베딩과 함께 결정한다.
- **번들러·TypeScript** — 런타임이 모듈로 갈라질 때 다시 본다.
- **오버뷰의 검색·챕터 접기** — 슬라이드 수가 수십을 넘는 덱을 아직 재지 않았다.
- **인쇄의 픽셀 게이트** — 페이지 수·비율·잉크까지만 본다 (같은 CSS의 다른 미디어다).
