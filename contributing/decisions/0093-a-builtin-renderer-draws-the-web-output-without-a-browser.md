# 0093 — 내장 렌더러는 웹 산출물을 브라우저 없이 배치하고 그린다 (`balpyo snap`)

- 상태: 확정 (실험 — 표면은 `balpyo snap` 하나다. 빌드 경로의 측정은 여전히 브라우저다)
- 날짜: 2026-10-11
- 관련: [ADR 0004](0004-geometry-side-table.md)(지오메트리 곁 표),
  [ADR 0064](0064-the-contract-is-component-and-layout-parity-not-pixel-parity.md)(동일성 계약),
  [ADR 0066](0066-preview-only-places-renders-side-by-side.md)(`preview`는 나란히 놓기만 한다),
  [ADR 0069](0069-onlyoffice-is-the-pptx-review-renderer.md)(PPTX 검수 렌더는 OnlyOffice)

## 맥락

덱을 쓰는 동안 결과를 보는 길은 둘이다. `watch`는 브라우저에서 웹을 보여 주고, `preview`는 웹 스크린샷과
OnlyOffice(없으면 LibreOffice)로 되돌린 PPTX를 나란히 놓는다. 둘 다 바깥 도구가 있어야 하고, `preview`의
PPTX 칸은 장당 수 초가 든다. 에이전트가 덱을 쓰고 고치는 고리, CI 로그에 그림을 붙이는 자리, 브라우저를
띄울 수 없는 기계에서는 "지금 이 슬라이드가 어떻게 생겼나"를 빠르게 물을 길이 없다.

빌드 자체가 이미 브라우저를 띄우는 이유는 배치다 — flex/grid와 테마의 레이아웃 CSS를 브라우저가 계산하고
지오메트리 패스가 그 결과를 잰다. 그래서 브라우저 없는 그림은 **배치를 누가 하느냐**의 문제다.

## 선택지

1. **브라우저로 찍는다.** 지오메트리 패스가 연 문서에서 슬라이드마다 스크린샷을 찍는다. 정확하지만 브라우저가
   있어야 한다는 사정이 그대로다 — 이 결정이 풀려는 문제가 바로 그것이다.
2. **덱 모델에서 직접 배치한다.** 덱 → 상자 트리 → 배치를 Go로 쓴다. 웹 렌더러가 덱을 HTML/CSS로 옮기는 해석
   (inline style, 슬롯 grid, 도형 ink, 크롬 띠)을 한 벌 더 만들게 되고, 두 해석이 갈라지면 미리보기가 기준
   타깃과 다른 것을 보여 준다.
3. **웹 산출물을 읽는 작은 브라우저를 쓴다.** 웹 렌더러가 낸 `index.html`을 그대로 입력으로 받아 CSS를 풀고
   배치하고 그린다. 배치 엔진은 새로 만들지만 덱을 웹으로 옮기는 해석은 웹 렌더러 하나뿐이다.

## 결정

**선택지 3.** `render/quick`이 웹 렌더러의 HTML을 배치하고 그린다.

1. **입력은 웹 렌더러의 산출물이다.** CSS cascade(`@layer` 순위 · 선택자 specificity · inline · 상속 ·
   `var()` · `calc()` · `hsl(from …)` · `color-mix()`)를 풀고, block · inline · flex · grid · table · 절대
   배치를 계산한다. 텍스트는 go-text(HarfBuzz 포트 · UAX #14 줄바꿈 · fontconfig 글꼴 목록)로 셰이핑한다.
   지원하는 범위는 **웹 렌더러가 내는 것**이다 — 일반 웹 페이지를 그리려는 엔진이 아니다.
2. **결과는 지오메트리 패스와 같은 꼴이다.** 측정 스크립트가 돌려주는 JSON과 같은 모양을 내고
   `geom.FromMeasurement`가 같은 대조(`newGeometry` · `Verify`)를 거쳐 `geom.Geometry`로 만든다. 그래서 배치
   진단과 PPTX 렌더러가 이 측정값을 그대로 소비할 수 있다.
3. **그림은 빌드와 같은 흐름이다.** 측정용 HTML을 배치해 지오메트리를 얻고, 그 박스로 연결선 · 잰 박스 도형을
   구운 최종 HTML을 다시 배치해 그린다. 그리기 순서는 CSS 2.1 부록 E의 간이판이다.
4. **CLI 표면은 `balpyo snap` 하나다.** 슬라이드마다 PNG, 덱 GIF(reveal 스텝마다 한 프레임), 잰 박스 · 식별자
   오버레이, 내장 측정의 배치 진단을 낸다. `build` · `check` · `watch` · `preview`의 측정은 바꾸지 않는다.
5. **기준은 여전히 브라우저다.** 산출물과 `--check-layout`의 판정은 브라우저 측정에서 나온다. 내장 렌더러는
   빠른 미리보기이고, 줄바꿈 · 글리프가 브라우저와 같다고 약속하지 않는다.
6. **엔진의 정확도는 박스로 잰다.** `TestDrift`가 예제 덱과 fixture의 같은 HTML을 브라우저와 내장 엔진으로 재고
   박스 rect를 견준다. 1px 안에 드는 박스가 99% 아래로 떨어지면 실패한다. 견주는 것은 계약의 단위인 rect이고,
   픽셀 · 줄 수는 보지 않는다.

## 근거

- 선택지 3은 "웹이 기준 타깃"을 구조로 지킨다. 덱을 웹으로 옮기는 해석이 웹 렌더러에만 있으므로, 웹 렌더러가
  바뀌면 미리보기도 따라 바뀐다. 갈라질 수 있는 것은 배치 알고리즘뿐이고, 그 갈라짐은 `TestDrift`가 숫자로 본다.
- 웹 렌더러가 쓰는 CSS가 닫혀 있다는 것이 이 선택을 현실적으로 만든다. 예제 · fixture 전체의 inline 속성은 50여
  종, 스타일시트 속성은 그보다 적고, SVG는 `rect` · `path` · `ellipse` · `circle` · 그라디언트 · 무늬 · 표식뿐이다.
- 처음 맞대 본 결과 예제 덱 넷과 fixture 스물넷의 박스 2191개가 모두 브라우저와 1px 안이었다 (한국어
  `keep-all` 줄바꿈 포함). 바닥을 100%가 아니라 99%로 둔 것은 글꼴 · 셰이퍼 판이 바뀌어 줄 하나가 갈리는 일을
  회귀로 보지 않기 위해서다.
- 측정을 지오메트리와 같은 꼴로 내면 미리보기의 진단이 빌드의 진단과 같은 코드(`geom.Diagnose`)에서 나온다 —
  `snap`의 경고를 읽는 방법이 `--check-layout`의 경고를 읽는 방법과 같다.

## 결과

- `render/quick`(배치 · 그리기)과 `internal/snapshot`(파일 쓰기), `balpyo snap`이 생긴다. `render/geom`에
  `FromMeasurement`가 더해진다.
- 의존성이 셋 늘어난다: `github.com/go-text/typesetting` · `golang.org/x/image` · `golang.org/x/net`(HTML 파서).
  모두 순수 Go다. 이 판들이 요구해 `go.mod`의 `go` 지시어가 `1.26.0`이 된다.
- 내장 엔진이 그리지 않는 것: `enter` 애니메이션의 중간 프레임, 컬러 이모지 비트맵, SVG `<text>`. 무늬 빗금은
  브라우저보다 조금 진하다.
- 열지 않은 것: `build` · `check` · `watch`가 내장 측정을 쓰는 선택(브라우저 없는 PPTX). 측정값은 이미 같은
  꼴이라 플래그 하나로 이어지지만, 산출물의 좌표 출처를 바꾸는 일이라 따로 정한다.
